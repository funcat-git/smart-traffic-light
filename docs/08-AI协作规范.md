# AI 协作规范

> 本组四个人全部依赖 AI 写代码。这不是问题——问题是**AI 写完的东西不算你的**，除非你能讲清楚。
> 本文规定：谁能用 AI 改什么、怎么问、怎么验收、怎么留痕，以及答辩时怎么答。

---

## 一、先定一个前提：AI 产出的代码是"租"来的

| | 自己写的代码 | AI 写的代码 |
|---|---|---|
| 所有权 | 你的 | 不确定 |
| 出错时 | 你知道去哪找 | 你不知道它为什么这么写 |
| 老师提问 | 能讲逻辑 | 只能背结论 |

**因此本组的规矩是**：AI 可以写 100% 的代码，但**每个进入 `main` 分支的功能，必须有一个组员能把它讲明白**。讲不明白的功能，不进仓库。

这条不是道德要求，是答辩的硬性风险：老师随便指一行问"这句为什么这么写"，答不上来，整组分数打折。

---

## 二、谁能用 AI 改什么（按目录划边界）

| 成员 | 可以用 AI 做的事 | 不可以用 AI 做的事 |
|---|---|---|
| **A 组长** | 生成/重构 `main.c` 状态机与配时算法；解释编译错误；核对定时器初值计算 | 让 AI 自己决定相位划分和配时参数（这是设计，必须人定） |
| **B 驱动** | 生成 `display.c` / `key.c` / `timer.c` 的驱动代码；优化消抖逻辑 | 让 AI 改 `system.h` 的引脚定义（会影响全局） |
| **C 仿真** | 查 Proteus 元件名称、报错含义、接线问题的排查思路 | 让 AI 生成原理图（它给不了 `.pdsprj`，只会瞎编） |
| **D 文档** | 润色报告措辞、生成表格、翻译术语、整理测试记录 | 让 AI 编造测试数据或实验结论 |

### 一条硬规则

> **`system.h` 只能由 A 修改，且只允许人改。**
>
> 理由：这个文件是全部引脚和参数的唯一真源。AI 改它一次，全组的代码可能集体跑偏，而且没人会立刻发现。所有 AI 生成代码的提示词里，都必须把 `system.h` 的**全文原文**贴进去当约束，而不是让它自己发挥。

## 三、怎么问（提示词模板，照抄）

### 反面教材（一定失败）

```
帮我写一个51单片机的交通灯程序
```

结果：AI 给你一份用 `delay(1000)` 阻塞、引脚随便定、没有状态机的代码。你还得推翻重写。

### 正确模板（四段式）

```
【项目背景】
51 单片机（AT89C51），12MHz 晶振，Proteus 仿真，Keil C51 编译。
十字路口信号灯，六相位状态机：南北绿→南北黄→全红→东西绿→东西黄→全红。

【硬约束 —— 必须严格遵守】
引脚定义（来自 system.h，不得改动）：
  ← 把 system.h 全文贴在这里 →
参数宏：GREEN_BASE=20, GREEN_MIN=12, GREEN_MAX=40, YEL_S=3, RED_S=2,
        EXT_CARS=3, EXT_STEP=5, GAP_S=4, EMG_S=8
禁止使用 delay() 或任何忙等循环——本工程用 T0 定时器 2ms 中断驱动。
禁止在中断服务函数里做耗时运算。
所有函数必须非阻塞。

【本次任务 —— 只做一件事】
只修改 display.c 中的 disp_scan()，实现 4 位数码管动态扫描。
不要改其他任何文件，不要改函数签名。

【输出要求】
1. 只输出完整可编译的 .c 文件内容
2. 每个函数上方用中文注释说明作用和调用时机
3. 在最后列出：你改了哪几行、为什么改
```

### 为什么这四段都要有

| 段落 | 缺了会怎样 |
|---|---|
| 项目背景 | AI 不知道是 51 还是 STM32，给的代码引脚全是错的 |
| 硬约束 | AI 默认用 `delay()`、默认随便定引脚，你后面全要返工 |
| 只做一件事 | 一次让它改 5 个文件，出错时你不知道是哪个改坏的 |
| 输出要求 | 它给你半截代码或伪代码，还要你再问一遍 |

## 四、验收：AI 交活后的五道检查

**每一份 AI 代码合并前，必须过这五关。** 有一关不过，打回重问。

### 检查 1：引脚核对（30 秒）

把代码里所有 `P1_0`、`P2`、`sbit` 之类扫一遍，对照 [hardware/引脚分配表.md](../hardware/引脚分配表.md)。

```
出现表里没有的引脚编号 → 打回
```

### 检查 2：搜 `delay`（10 秒）

```
整个工程搜 "delay" 和 "while("
出现 delay() → 打回，这是阻塞写法，会毁掉数码管刷新和按键响应
出现 while(条件) 在中断里 → 打回，中断不能等待
```

### 检查 3：定时器初值（1 分钟）

12MHz 晶振、1 个机器周期 = 12 个时钟 = 1μs。

| 想要的周期 | 初值计算 | 十六进制 |
|---|---|---|
| 2ms（本工程用） | `65536 - 2000` | `0xF830` |
| 1ms | `65536 - 1000` | `0xFC18` |
| 50ms | `65536 - 50000` | `0x3CB0` |

初值对不上，倒计时就不准，而且现象很隐蔽（差一点，以为是正常的）。

### 检查 4：编译 + 仿真（5 分钟）

```
Keil 编译 → 必须 0 Error
Proteus 加载新 HEX → 必须实际跑一遍，不能"看起来对"
```

### 检查 5：讲解测试（最重要，2 分钟）

**从组里随便挑一个人（不是改代码的那个），指着新代码问："这段在干什么？"**

- 答得出来 → 通过
- 答不出来 → **不许合并**，让改代码的人讲给全组听，讲完再合并

> 这一关是整份规范的核心。它保证了：不管代码是 AI 写的还是谁写的，组里始终有人懂。

## 五、必须能讲出来的六件事（答辩必问）

代码可以全由 AI 生成，但这六条必须人脑里装着：

### 1. 为什么不用 `delay()`

> 因为 `delay()` 是忙等，CPU 卡在循环里什么都干不了。这个项目里数码管要每 2ms 刷新一次才不闪，按键要每 16ms 采样一次才不丢。用了 `delay(20000)` 表示绿灯 20 秒，那 20 秒内数码管停止刷新、按键完全失灵。所以我用定时器中断 + 状态机，把"等待"变成"计数"。

### 2. 定时器初值 `0xF830` 怎么来的

> 12MHz 晶振，12 分频后机器周期是 1μs。要 2ms 中断一次，就是 2000 个机器周期。定时器是向上计数、溢出中断，所以从 `65536 - 2000 = 63536` 开始数，63536 就是 `0xF830`。

### 3. 数码管为什么要消隐

> 动态扫描是轮流点亮 4 位。如果直接改段码再改位选，中间那一瞬间新段码会显示在旧位上，产生"重影"。所以顺序必须是：先关段码（`SEG_PORT = 0x00`）→ 再换位选 → 再给新段码。

### 4. 自适应配时的两条规则

> 第一条延长：绿灯期间每秒统计本方向来了几辆车，累计满 3 辆就延长 5 秒，最多延长到 40 秒。第二条截止：连续 4 秒没有车、且已经放行了至少 12 秒，就立即结束绿灯，把时间让给对方方向。两条规则一个管"有车多放"，一个管"没车快放"。

### 5. 为什么黄灯是 3 秒

> 依据《GB 14886-2016 道路交通信号灯设置与安装规范》，城市道路黄灯时长 3 秒。这是国家标准给的，不是我随便定的。

### 6. 中断服务函数里为什么只置标志位

> 中断应该尽量短。我在 2ms 中断里只做三件事：刷新一位数码管、采样按键、每 500 次置一个 `sec_flag`。真正复杂的逻辑（配时计算、相位切换）全部放在主循环里，看到 `sec_flag` 才做一次。这样中断耗时几个微秒，不会影响其他中断。

## 六、留痕：每个 commit 标注 AI 参与度

在提交信息末尾加一行 `AI:` 标签。这不是为了追责，是为了**以后出问题时知道先怀疑哪部分**。

| 标签 | 含义 |
|---|---|
| `AI: none` | 完全手写 |
| `AI: assist` | AI 给了思路/片段，人改写整合 |
| `AI: generate` | AI 生成整段，人核对后使用 |
| `AI: review` | 人写完，AI 帮忙查错 |

**示例**：

```
feat: 增加夜间黄闪模式

AI: generate
已核对：引脚对照引脚表无新增，未引入 delay，Proteus 实测通过，
讲解人：B（讲解测试于 W4 例会）
```

`AI: generate` 的提交**必须**附上"已核对"三行：引脚、delay、实测。缺一项组长不合并。

## 七、绝对不要做的事

| ❌ 不要 | 后果 |
|---|---|
| 把 AI 代码直接 commit，不编译 | 编译不过时你不知道错在哪，因为不是你写的 |
| 让 AI 一次改 5 个文件 | 出问题无法定位，只能全回滚 |
| 让 AI 改 `system.h` | 全组代码集体跑偏 |
| 用 AI 编造测试数据填进报告 | 老师现场让你复现，做不出来 |
| 让 AI 写"实验现象"描述 | 同上，且一读就是 AI 腔 |
| 答辩稿让 AI 生成后直接背 | 老师换个问法就答不上 |
| 让 AI 决定配时参数 | 参数背后要有理由，AI 给的理由是编的 |

## 九、每周 AI 使用复盘（5 分钟，例会最后一项）

固定问三个问题，D 同学记进 `CHANGELOG.md`：

1. **这周 AI 写的代码，有没有哪段到现在还没人完全讲明白？** → 有就当场指定人弄懂
2. **有没有哪次 AI 给的东西是错的，我们差点用了？** → 记下来，是宝贵经验
3. **下周有没有需要提前问 AI 的设计问题？** → 提前问，别临时抱佛脚

### 典型案例记录格式

```markdown
### AI 踩坑记录
- **2026-11-28** AI 生成的 disp_update 里，红灯剩余时间算成了
  `rem + YEL_S + RED_S + 1`，多算 1 秒。原因：它把"当前秒"和"已过秒"搞混。
  发现方式：人工核对真值表。教训：涉及边界加减的算式，必须用真值表逐行验。
```

**这些记录在结题报告里是加分项**——说明你们不是无脑用 AI，而是有方法地管住了它。

## 十、中文注释的编码坑（必看，会白干半天）

代码里全是中文注释，这在 Keil 里是个真实地雷。

### 现象

| 现象 | 原因 |
|---|---|
| Keil 打开源文件，中文全是乱码 | 文件是 UTF-8，但 Keil 默认按 GBK 解析 |
| 编译报 `error C129: missing ';' before ...` 指向注释行 | 最后一个汉字的第二个字节被误认成语法符号 |
| Proteus 里现象正常，但改一行注释就编译不过 | 同上，注释里的字节恰好撞上控制字符 |
| Git diff 显示整个文件都变了 | 换行符 CRLF/LF 混用，或编码被编辑器改过 |

### 本组的统一规定

1. **所有 `.c` / `.h` 文件使用 UTF-8（无 BOM）**
2. **Keil 里设置一次，全组统一**：
   ```
   Edit → Configuration → Editor 标签
     Encoding: 选 UTF-8
     ✅ 勾选 "Auto Detect Encoding"
   ```
3. **提交前跑检查脚本**，第 9 项会报出非 UTF-8 的文件
4. 如果还是乱码：VS Code 打开 → 右下角点编码 → **Save with Encoding** → UTF-8（不要带 BOM）

### 为什么强调"无 BOM"

Keil C51 对 BOM 处理不一致，带 BOM 时第一个字符可能被当成非法 token，报的错还指向无关的行。检查脚本第 9 项会提示。

### 行尾符

`.gitattributes` 已配好：提交时统一 LF，检出时按平台转换。**不要手动改这个文件**，改了会导致全组 diff 爆炸。
