# 智能交通灯控制系统 —— 方案设计书

> 工训项目 · 选题二（难度：高）· 4 人小组
> 开发环境：Proteus 8.x + Keil uVision (C51)
> 核心器件：AT89C51 @ 12MHz

---

## 一、需求分析

### 1.1 题目要求拆解

| 原文要求 | 落地设计 |
|---|---|
| 设计实现智能交通灯控制系统 | 十字路口六相位状态机（南北绿/黄、东西绿/黄、全红清空） |
| 分析智能交通灯运行逻辑 | 用有限状态机 FSM 描述相位迁移，画出状态迁移图 |
| **通过传感器采集车流量信息** | 两个按键模拟地感线圈，每按一次 = 一辆车通过；绿灯期内统计车数 |
| **设计算法** | 车辆感应自适应配时算法：需求延长 + 空放截止 |
| 编写程序 | C51 模块化代码（main / display / key / timer） |
| 用 Proteus 设计与仿真 | 完整原理图 + HEX 装载 + 交互测试 |

### 1.2 "智能"体现在哪（这是拿高分的关键）

普通组只能做"固定 20 秒循环"，我们做三件事体现智能：

1. **感应自适应配时**：绿灯时长在 12~40s 之间动态浮动。来车多就延长，连续 4 秒没车就提前切走。
2. **紧急车辆优先**：按下紧急键，立即插入 8 秒全红清空，清障后回到正常调度。同时蜂鸣器提示。
3. **夜间低峰模式**：黄灯 1Hz 闪烁，倒计时熄灭。模拟深夜 22:00 后的路口策略。

再附加 **人行横道灯联动**（行人灯与同向机动车灯同步，"红灯停、绿灯行"），这是交通工程的规范要求，答辩时能讲出专业度。

## 三、交通灯运行逻辑（FSM 状态机）

### 3.1 状态迁移图

```
          ┌──────────────────────────────────────────────┐
          │                                              │
          ↓                                              │
   ┌─────────────┐  计时到  ┌─────────────┐  计时到  ┌──────┴──────┐
   │ PH_NS_G     │────────→│ PH_NS_Y     │────────→│  PH_R1      │
   │ 南北绿 20s  │         │ 南北黄 3s   │         │ 全红清空 2s │
   │ (可自适应)  │         └─────────────┘         └──────┬──────┘
   └──────▲──────┘                                       │
          │                                              ↓
   ┌──────┴──────┐  计时到  ┌─────────────┐  计时到  ┌──────┴──────┐
   │ PH_R2       │←────────│ PH_EW_Y     │←────────│  PH_EW_G    │
   │ 全红清空 2s │         │ 东西黄 3s   │         │ 东西绿 20s  │
   └─────────────┘         └─────────────┘         └─────────────┘

   任意相位 ──[紧急键]──→ PH_EMG（全红 8s）──→ PH_NS_G
   任意相位 ──[夜间键]──→ 夜间黄闪（时间冻结）──[再按]──→ 恢复原相位
```

### 3.2 相位时序真值表（默认配时）

| 时段 | 时长 | 南北 红/黄/绿 | 东西 红/黄/绿 | 南北显示 | 东西显示 |
|---|---|---|---|---|---|
| T0 南北通行 | 20s | 0/0/**1** | **1**/0/0 | 20→1 | 25→6 |
| T1 南北黄灯 | 3s | 0/**1**/0 | **1**/0/0 | 3→1 | 5→3 |
| T2 全红 | 2s | **1**/0/0 | **1**/0/0 | 2→1 | 2→1 |
| T3 东西通行 | 20s | **1**/0/0 | 0/0/**1** | 25→6 | 20→1 |
| T4 东西黄灯 | 3s | **1**/0/0 | 0/**1**/0 | 5→3 | 3→1 |
| T5 全红 | 2s | **1**/0/0 | **1**/0/0 | 2→1 | 2→1 |

一个完整周期 = 50 秒（基础配时）。

**倒计时显示规则（答辩必问）**：屏幕显示的是"本方还能通行/还需等待多少秒"，即
- 绿灯方向：显示本向绿灯剩余秒数；
- 红灯方向：显示"本向剩余绿灯 + 黄灯 + 全红"的合成时间，即距本向变绿的秒数。

两条规则保证两个方向读数之和恒等于一个红灯周期的长度，符合真实路口的对向倒计时规律。

## 四、核心算法：车辆感应自适应配时

### 4.1 算法思想

真实路口的感应控制（Vehicle-Actuated Control）逻辑是：**绿灯有一个最小保证时长，只要还有车来就不断延长，直到达到最大时长；如果车流断了，就提前结束。**

我们用两个计数器实现：

| 变量 | 含义 |
|---|---|
| `phase_total` | 当前相位应持续的秒数（可动态变化） |
| `phase_elapsed` | 已过秒数 |
| `car_cnt` | 本绿期内累计来车数 |
| `gap_cnt` | 连续无来车的秒数 |

### 4.2 算法伪代码

```
每 1 秒：
    累加本向来车数到 car_cnt
    若无车: gap_cnt++    否则: gap_cnt = 0

    // 规则①：需求延长
    若 car_cnt >= 3:
        car_cnt = 0
        若 phase_total + 5 <= 40:  phase_total += 5

    // 规则②：空放截止
    若 gap_cnt >= 4 且 phase_elapsed >= 12 且 phase_elapsed < phase_total:
        phase_total = phase_elapsed       // 立即进入黄灯

    若 phase_elapsed >= phase_total:  切换到下一相位
```

### 4.3 参数设计依据

| 参数 | 取值 | 依据 |
|---|---|---|
| GREEN_BASE | 20s | 中等流量路口的常规配时 |
| GREEN_MIN | 12s | 必须保证排队车辆能启动并清空，一般 ≥ 10s |
| GREEN_MAX | 40s | 防止单方向长时间占用，避免对向等待过长 |
| EXT_STEP | 5s | 单车到达间隔约 2s，延长 5s 可放行 2~3 辆 |
| EXT_CARS | 3辆 | 累计 3 辆才触发一次延长，抑制抖动 |
| GAP_S | 4s | 车头时距超过 4s 视为车流中断 |
| YEL_S | 3s | 国标黄灯时间 3s |
| RED_S | 2s | 全红清空，防止尾车与横向首车冲突 |
| EMG_S | 8s | 紧急车辆通行所需时间 |

> 黄灯 3 秒、全红 2 秒对应《道路交通信号灯设置与安装规范》GB 14886 的常规取值，答辩时能说出来就是加分项。

### 4.4 传感器方案说明（题目要求"传感器采集车流量"）

Proteus 里没有真实的地感线圈，我们用**按键脉冲模拟车检器输出**：每按一次代表一辆车驶过检测断面，产生一个下降沿。这在答辩时必须讲清楚——**按键不是按钮功能，而是车检器信号的等效模型**。

如果要换成真实传感器（实物演示可选）：

| 传感器 | 原理 | 与单片机接口 | 说明 |
|---|---|---|---|
| 红外对射管 | 车遮挡光路 → 输出电平翻转 | 比较器 LM393 → P3.4/P3.5 | 最便宜，适合课设 |
| 地感线圈 | 车体改变线圈电感 → 振荡频率变化 | 振荡电路 + 整形 → 外部中断 | 真实路口方案，成本高 |
| 超声波 HC-SR04 | 测距突变判定有车 | Trig/Echo → 定时器测距 | 需占用一个定时器资源 |

无论哪种，软件接口都是同一个：**检测到一次电平下降沿 → `car_ns++`**。所以我们的 `key_scan()` 函数在实物板上可以直接接传感器输出，不需要改逻辑。这是模块化设计的好处。

### 4.5 演示话术（怎么让老师看到"智能"）

1. 上电正常循环，报告"当前是固定基础配时"。
2. 连续按 3 次【南北车辆检测】→ 屏幕南北绿灯读数从 20 **跳到 25**，说明需求延长生效。
3. 再连按 9 次 → 读数继续跳到 30、35、40 封顶，说明上限保护生效。
4. 什么都不按 → 绿灯剩 12 秒时**提前跳黄灯**，说明空放截止生效。
5. 按【紧急】→ 立刻全红 + 蜂鸣器，8 秒后恢复。

## 五、软件架构

```
code/
├── system.h     引脚定义、参数宏、全局声明
├── main.c       主程序：状态机 + 配时算法
├── display.c    数码管动态扫描 + 倒计时合成
├── key.c        按键消抖 + 车流统计
└── timer.c      T0 中断：2ms 时基
```

### 5.1 时间基准

| 任务 | 周期 | 实现方式 |
|---|---|---|
| 数码管扫描 | 2ms/位 | T0 中断内调用 `disp_scan()` |
| 按键扫描 | 16ms | T0 中断内 8 次分频调用 `key_scan()` |
| 秒节拍 | 1000ms | `tick >= 500` 置 `sec_flag`，主循环处理 |

关键点：**中断里只做最短的时基动作，所有业务逻辑放主循环**，避免中断超时导致数码管闪烁。这是嵌入式编程的基本功，答辩时强调这一点。

### 5.2 为什么不用 delay()

`delay()` 会阻塞 CPU，导致动态扫描中断、按键丢失。我们用"定时器中断 + 标志位 + 主循环轮询"的非阻塞架构，单片机可以同时"看表、扫屏、听按键"。这是方案技术含量的体现点。

## 九、风险与预案

| 风险 | 预案 |
|---|---|
| 数码管不亮 / 显示乱码 | 检查 P0 上拉排阻；确认使用的是 CC（共阴）版本，或改 `SEG_COMMON_CATHODE` 宏 |
| 数码管有鬼影 | 扫描函数里先 `SEG_PORT = SEG_OFF` 再切换位选（代码已实现） |
| 按键抖动导致车数虚增 | 16ms 周期采样 + 2 次一致确认的消抖（代码已实现） |
| Proteus 仿真卡顿 | 关闭 "Use animated LED"，降低仿真帧率 |
| 倒计时读数对不上 | 用相位时序真值表逐段核对 `disp_update()` |
| 时间不够 | 砍掉人行灯与蜂鸣器，保留三大核心功能；自适应配时是难点也是评分点，不能砍 |
