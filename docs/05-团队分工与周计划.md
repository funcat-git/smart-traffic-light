# 团队分工与周计划

## 一、四人分工

| 代号 | 角色 | 姓名 | 核心职责 | 交付物 | 技能要求 |
|---|---|---|---|---|---|
| **A** | 组长 / 系统集成 | 待填 | 状态机设计、主程序、仓库管理、答辩主讲 | `main.c`、`system.h`、方案设计书 | 能看懂 C 语言 if/switch |
| **B** | 驱动开发 | 待填 | 数码管扫描、按键消抖、定时器 | `display.c`、`key.c`、`timer.c` | 理解中断概念 |
| **C** | 仿真与硬件 | 待填 | Proteus 原理图、元件选型、接线图 | `.pdsprj`、引脚表、元件清单 | 会用 Proteus 拖元件 |
| **D** | 测试与文档 | 待填 | 测试用例、结题报告、PPT、例会记录 | 报告、PPT、`CHANGELOG` | 会写文档、会用 PPT |

### 分工原则

- **每人有独立目录**，互不干扰（见 CONTRIBUTING.md 第二节）
- **每人有明确交付物**，周末检查时能拿出东西
- **技能门槛最低化**：A 和 B 只需要看懂 C 语言基础；C 只需要会拖元件连线；D 完全不需要写代码

### 如果只有 3 个人

把 D 的文档工作分给 C（C 的工作量在 W1-W2 较少），A 兼管 PPT。

## 一之二、分工分三次定，不是一个时点

> **结论：骨架搭好后定「责任域」，最小闭环跑通后定「任务分配」，中期后定「冲刺分配」。现在只能定第一种。**

### 为什么不能一次定死

分工的本质是**分配不确定性**，不是分配工作量。你不知道的事情没法分：

| 时点 | 你已经知道什么 | 你还不知道什么 | 所以能定什么 |
|---|---|---|---|
| **现在**（骨架已搭） | 目录结构、文件接口（`system.h` 的引脚和函数签名） | 谁写代码快、谁调试强、哪个环节会卡住 | ✅ **责任域**：谁拥有哪个文件 |
| **最小闭环跑通后** | 整条链路耗时、谁哪里卡过、真实工作量分布 | 各功能模块的难度、测试会暴露什么问题 | ✅ **任务分配**：谁做哪个功能 |
| **中期检查后** | 已完成 vs 计划的差距、已知 bug 列表 | 答辩会遇到什么追问 | ✅ **冲刺分配**：谁补哪个缺口 |

**在骨架阶段就分到"你这周做数码管驱动"，是空头承诺。** 因为到时候你会发现数码管比想象中难三倍，而按键比想象中简单十倍。

### 什么叫「最小闭环」

**一条端到端能跑通的链路：**

```
改一行代码 → Keil 编译出 HEX → 加载进 Proteus → 看到灯按预期变化
```

具体要求（就是 W1 关卡 1）：

- [ ] Keil 里能编译出 `.hex` 文件
- [ ] Proteus 里有 AT89C51 + 最小系统 + **一个** LED
- [ ] 加载 HEX 后，**这个 LED 亮**
- [ ] 改一行代码（比如 `P1 = 0xFE` 改成 `P1 = 0xFD`），重新编译加载，**灯换位置亮**

**只有第四条做到，才算闭环通了。** 因为这说明"改代码 → 看效果"的循环成立，而不只是碰巧跑起来一次。

**预计耗时：1~3 天**（软件装得顺利的话，一天就够）。

### 为什么闭环之前不谈任务分工

三个理由：

1. **接口还没被验证**。`system.h` 里的引脚定义是纸上设计的，闭环跑通才知道对不对。如果现在把 `display.c` 派给 B，结果闭环时发现数码管位选接法要改，B 的工作全废。
2. **不知道瓶颈在哪**。可能 Keil 装三天装不上，也可能 Proteus 元件库缺件。这些风险要在闭环阶段暴露，而不是在分工后暴露。
3. **不知道谁真的会什么**。组员说"我会 C 语言"，和"能在 51 上写出不阻塞的中断服务函数"，是两件完全不同的事。闭环阶段每个人都会碰一遍工具链，这时候你才看得出谁上手快。

### 第一次分工（现在就能做，10 分钟）

**只定责任域，不定任务。** 填进这张表，然后各人只在自己那一列动手：

| | A | B | C | D |
|---|---|---|---|---|
| **拥有（可以改）** | `main.c`、`system.h`、根目录配置 | `display.c`、`key.c`、`timer.c` | `simulation/`、`hardware/`、`docs/images/` | `report/`、`docs/04`、`CHANGELOG.md` |
| **闭环阶段盯什么** | 装 Keil、编译出第一个 HEX | 装 Keil 跟上（练手，不上传） | 装 Proteus、画最小系统 | 学看代码、准备测试记录模板 |
| **闭环阶段交付** | 点灯 HEX | 自己电脑上能编出同样的 HEX | Proteus 里 LED 亮 | 一份空白测试记录表 |

**关键约束**：闭环阶段**谁都别写业务代码**。这周的唯一目标是把链路跑通，写业务逻辑是下周的事。

### 第二次分工（闭环通了，30 分钟会议）

闭环跑通后开一次会，先回答三个问题，再分任务：

1. **Keil 装了几次才成？卡在哪？** → 知道谁的工具链最稳，以后编译由他兜底
2. **Proteus 接线花多久？哪一步最费时？** → 知道 C 的真实工作量，任务量据此分配
3. **每个人在这三天里感觉最难的是什么？** → 这是能力匹配的唯一可靠依据

然后按真实难度分，**不要按"每人四分之一"分**。

### 反直觉的一条：四个人别平均分

单片机项目的工作量是**高度不均匀**的，实际大致是这样：

```
核心代码（状态机 + 配时算法）  ████████████████  40%
驱动代码（数码管/按键/定时器）  ██████████        25%
仿真搭建（原理图 + 联调）      ████████          20%
测试文档（用例/报告/PPT）      ██████            15%
```

如果硬按 25% 平均分，结果是：A 干不完，D 早早闲下来。

**更合理的分配：1 人主攻 + 1 人辅助 + 2 人验收。**

| 模式 | 怎么运作 |
|---|---|
| **主攻**（1 人） | 拿最大那块，允许他进度慢但不能断 |
| **辅助**（1 人） | 跟主攻同方向，随时补位、写测试代码验证 |
| **验收 1**（1 人） | 不看代码只看现象：仿真跑不跑得通、数码管对不对 |
| **验收 2**（1 人） | 讲解测试的执行者：随机指一段代码问"这是干嘛的" |

**为什么"闲"的人不是浪费**：AI 协作规范里最关键的第 5 关（讲解测试），必须有"不看代码的人"来执行才有意义。如果他们也在写代码，就会本能地觉得"我写的肯定对"，这一关就形同虚设。

### 三次再平衡点

分工不是一次定完就不动。**固定三个时点重新看一次**：

| 时点 | 看什么 | 什么时候调整 |
|---|---|---|
| 第 3 天（闭环后） | 谁卡过、谁上手快 | 任务量按真实难度重分 |
| 第 3 周末（中期前） | 已完成 vs 计划差距 | 进度落后的人减任务，不让他拖死全组 |
| 第 5 周初（测试开始） | 已知 bug 数量 | 全员转测试，写代码的人一起去查 |

**判断要不要调的信号**：

- 某人连续两天群里没声音 → 大概率卡住了但没敢说
- 某块任务原估 2 天，第 3 天还没动静 → 立刻拆小或换人
- 两个人同时没事干 → 任务分错了，重新看分布

## 一之三、「把任务切均匀」为什么在本项目里做不到

> 常见反驳：**"任务切细一点，切到每人一样多，不就行了？"**
>
> 方向对，这是标准的 WBS（工作分解）。但本项目有四个硬约束，让"均匀"只能是表格上的假均匀。

### 约束 1：同一个项目里，任务块的大小差 10 倍以上，而且切不动

真实切分会是这样（按"可独立验证的行为"切）：

| # | 任务块 | 归属 | 真实耗时 |
|---|---|---|---|
| 1 | 最小系统跑通 + 点灯 | A/C | **3 天**（含装软件踩坑） |
| 2 | 6 盏信号灯接线 | C | 1 小时 |
| 3 | 灯态输出函数（`lights_update`） | A | 3 小时 |
| 4 | 数码管接线 + P0 上拉 | C | 4 小时 |
| 5 | 4 位动态扫描代码 | B | 1 天 |
| 6 | 按键接线 | C | 1 小时 |
| 7 | 消抖代码 | B | 半天 |
| 8 | 2ms 定时器中断 | B | 半天 |
| 9 | 六相位状态机 | A | **2 天** |
| 10 | 倒计时合成逻辑 | A | 半天 |
| 11 | 自适应配时 | A | 1 天 |
| 12 | 人行灯 + 蜂鸣器 | C | 2 小时 |

**看出来问题了吗**：第 1 块 3 天，第 6 块 1 小时——**差 24 倍**。

想切均匀，就得把第 1 块切碎。但第 1 块恰恰**切不动**：它就是"Keil 编译出 HEX → Proteus 跑起来"这一个闭环。这中间任何一步断掉，整个块就是 0 进度。你没法让两个人各"装一半 Keil"。

### 约束 2：强耦合的块不能拆给两个人

第 9 块"六相位状态机"2 天，能不能拆成"南北 1 天 + 东西 1 天"？

**不能。** 因为它在代码里是同一个函数：

```c
switch (phase)          /* ← 一个 switch，六个数级 */
{
    case PH_NS_G: ...
    case PH_EW_G: ...
}
```

两个人写这个 switch 的两半，必然同时改同一个文件、同一个函数 → 每次提交都冲突。冲突解决的时间比写代码还长。

**可切性受限于耦合度**，不受限于你多想要均匀。

### 约束 3：不同块的技能栈不同，切了也不能互换

"均匀分块"的隐含前提是：**每块需要的能力一样，所以谁都能干哪块**。本项目不成立：

| 块类型 | 需要什么 | 谁能干 |
|---|---|---|
| 写 C 代码 | 懂中断、懂寄存器 | A、B |
| 画原理图 | 会用 Proteus、认元件 | C |
| 写文档 | 会写、会用 Word/PPT | D |
| 测试执行 | 细心、能对照真值表 | 谁都行 |

所以"你干完你的来帮我"这句话在本项目里**不成立**——A 的活 C 接不了，C 的活 A 也不熟。

### 约束 4：新手估工时的误差是 3 倍

你说"这块 2 天"，实际可能 6 天，也可能 8 小时就完事。

**所以任何计划表上的"均匀"都是假均匀**：写的时候看起来每人 25 天，第三周就发现有人落后一周、有人闲着。

> 经验值：第一次做某个技术栈（你们现在就是），单块工时估算平均偏低 **2~3 倍**。这不是你们的问题，是所有人的问题。

---

### 那真正可行的做法是什么

#### 做法 1：按「周里程碑」对齐，而不是按「任务」分派

不要让四个人各干各的活，**让四个人盯着同一个周末目标，各自负责其中一部分**。

| 周 | 全员共同目标 | 各人负责的部分 |
|---|---|---|
| W2 | **8 个灯能按代码亮灭** | A 状态机 / B 数码管+按键 / C 接线 / D 记录现象 |
| W3 | **完整跑完 50 秒周期** | A 配时调参 / B 时序核对 / C 加载调试 / D 记测试 |
| W4 | **5 个按键全有反应** | A 紧急夜间 / B 消抖 / C 蜂鸣器 / D 用例执行 |

这样即使有的块大有的块小，**所有人的进度指针都指向同一个格子**，谁落后一眼看得见。

#### 做法 2：不均匀就承认，用"验收岗"吸收余量

前面说过 1 主攻 + 1 辅助 + 2 验收。**验收岗不是闲人，是余量吸收池**：

- 主攻卡住 → 辅助顶上
- 辅助也卡 → 验收岗转去写测试用例（这活永远干不完）
- 全部顺利 → 验收岗提前做下周的准备工作

**关键是：让"闲着"变成有用的动作，而不是等任务。**

#### 做法 3：什么情况下"均匀切"真的可行

有，而且本项目里就有：

| 任务 | 能不能均匀切 | 为什么 |
|---|---|---|
| 写 13 条测试用例 | ✅ 能 | 同质、独立、无耦合，4 人各 3~4 条正好 |
| 整理答辩 PPT 12 页 | ✅ 能 | 同上 |
| 查阅元件参数 | ✅ 能 | 同上 |
| 写状态机代码 | ❌ 不能 | 强耦合、需专业能力 |
| 画 Proteus 原理图 | ❌ 不能 | 只有一份文件，二进制无法合并 |

**判据：能均匀切 ⇔ 各块同质 + 无共享文件 + 无接口依赖。** 满足就切，不满足就别硬切。

---

### 一句话

> **均匀分块是"给同质任务用的工具"，不是"给异构项目用的公式"。**
> 这个项目里 80% 的工作量集中在 2 个人手上，剩下 20% 分给另外 2 个人——这不是分工失误，是任务本身的结构。
> 与其硬把 40% 的活切成 25%，不如承认它，然后把调度做对（按周对齐 + 验收岗吸收余量）。

## 三、每周例会（15 分钟，站着开）

**时间**：每周日晚 20:00（线上，腾讯会议/微信语音）
**主持**：组长轮值（第一周 A，第二周 B，依此类推）
**记录**：D 同学，会后发群里

### 固定四问

1. **上周说好要做的，做完了吗？** 没做完 → 卡在哪一步，具体到什么程度
2. **这周做什么？** 每人说一条，具体到文件名
3. **有没有卡住需要别人帮的？** 有就当场约时间
4. **有没有改到别人负责的目录？** 有就赶紧说，避免后续冲突

## 四、风险预案

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| 某人连续两周没进度 | 中 | 高 | 第 2 周例会点名，组长拆分任务给其他人 |
